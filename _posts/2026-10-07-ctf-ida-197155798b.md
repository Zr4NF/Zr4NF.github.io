# IDA 逆向与恢复笔记

## 1. 目标

这个二进制是一个 64 位 C++ 程序，主体不是壳，也没有复杂反调试。核心工作不是脱壳，而是：

1. 识别主菜单分发逻辑。
2. 把 runtime state、task descriptor、session object 三类核心对象恢复出来。
3. 找到真正触达 `/flag`、`./flag` 的代码路径。
4. 判断菜单功能之间的状态流转，尤其是 session 生命周期和回收后的残留指针。

当前 IDA 里已经确认的关键点：

- `run_gateway_menu`：`0x8A60`
- `parse_u64_trimmed`：`0x2D30`
- `register_model_artifact`：`0x4230`
- `stream_artifact_chunk`：`0x7FB0`
- `bootstrap_async_scheduler`：`0x36A0`
- `patch_session_metadata`：`0x55B0`
- `audit_snapshot_read_flag`：`0x6750`
- `postproc_xor_scramble`：`0x2C50`
- `postproc_clear_negative_bytes`：`0x34E0`
- `postproc_shift_right_bytes`：`0x3520`

## 2. 总体逆向思路

### 2.1 先从主菜单建全局认知

先看 `run_gateway_menu(0x8A60)`，这里会直接打印菜单文本：

- `[1] Register model artifact`
- `[2] Stream artifact chunk`
- `[3] Bootstrap async scheduler`
- `[4] Inspect scheduler queue`
- `[5] Allocate session tensor`
- `[6] Complete batch inference`
- `[7] Patch session metadata`
- `[8] Provision worker profile`
- `[9] Dispatch async task`
- `[10] Runtime telemetry`
- `[11] Operator handbook`
- `[0] Shutdown gateway`

这一步的意义是先建立功能图，而不是一开始埋头看某个大函数。

你应该先把每个 case 对应函数记下来，再进入各功能函数。

### 2.2 优先看有输入、分配、写内存、调函数指针的路径

从利用和恢复角度，优先级建议如下：

1. `register_model_artifact`
2. `stream_artifact_chunk`
3. `allocate_session_tensor`
4. `complete_batch_inference`
5. `patch_session_metadata`
6. `runtime_telemetry`
7. `audit_snapshot_read_flag`

理由：

- 1 和 2 控制数据如何进入 artifact 内存。
- 3 和 4 决定 session 结构和生命周期。
- 5 明显是 patch 面。
- 6 会把内部状态打印出来，适合验证结构体恢复。
- 7 是唯一明显读 flag 的 sink，必须单独确认。

### 2.3 先恢复“状态对象”，再恢复“业务动作”

不要先试图完全理解每个函数的业务含义。先恢复对象布局：

- runtime state
- session
- task descriptor
- scheduler ctrl

对象布局一旦恢复出来，后面的业务逻辑会自然清晰。

## 3. 关键逻辑结论

### 3.1 `audit_snapshot_read_flag` 是直接读 flag 的位置

函数 `0x6750` 已确认：

- 先 `open("/flag", 12)`
- 失败再 `open("./flag", 12)`
- 成功就 `getline` 读取一行
- 最终打印 `[audit] snapshot: ...`

这说明：

1. 这里是明确的 flag 文件读取点。
2. 如果题目能控制这条路径被调用，或者能把函数指针改到这里，就可能直接出 flag。

### 3.2 session 对象是当前最关键的数据结构

`allocate_session_tensor(0x4D60)` 分配了一个 `0x50` 字节对象。

目前可恢复的关键字段：

```c
struct session_obj {
    uint32_t slot_id;          // +0
    uint32_t payload_size;     // +4
    void *payload_ptr;         // +8
    char alias[32];            // +16
    uint64_t generation;       // +48
    void (*postproc_fn)(void*);// +56
    // 后面还有未完全命名字段
};
```

这个恢复依据来自 `0x4D60` 和 `0x3910`：

- `+8` 被当作 payload 指针申请和释放。
- `+4` 被当作长度。
- `+16` 被 `snprintf("%s", alias)` 写字符串。
- `+56` 被当作函数指针调用。

### 3.3 session 生命周期存在明显的“回收后残留句柄”

`complete_batch_inference(0x3910)` 的关键流程：

1. 取 slot 对应的 session 指针。
2. 可能先对 payload 做一轮按字节变换。
3. 调用 `session->postproc_fn(session)`。
4. `free(session->payload_ptr)`。
5. `operator delete(session, 0x50)`。
6. 清掉 active 标记：`runtime_state + 360 + slot = 0`。

但它没有同步清掉 slot 数组里保存的 session 指针。

这意味着：

- active 标志被清了。
- 但句柄槽位里可能还留着 stale pointer。

这正是后续 `patch_session_metadata` 为什么要求 recycled session 的关键线索。

### 3.4 `patch_session_metadata` 是受限写原语

`patch_session_metadata(0x55B0)` 会要求输入：

- `diag.session.slot`
- `diag.qword_index`
- `diag.qword_value`

它会检查：

- slot 合法
- session handle 非空
- session 当前不是 active
- `qword_index == 0`

然后执行：

```c
*session_handle = user_qword_value;
```

也就是只允许改 stale session 对象的第一个 qword。

当前这个写原语是“受限 qword 写”，还不是任意写，但已经足够成为重点利用面。

### 3.5 `runtime_telemetry` 是结构恢复的最佳辅助函数

`runtime_telemetry(0x5D60)` 会打印：

- artifact arena 地址
- scheduler ctrl 地址
- strict_policy
- 默认 postproc 函数地址
- audit sink 地址，即 `audit_snapshot_read_flag`
- 每个 session slot 的 handle 和前两个 qword
- autoscaler profile 数组
- scheduler head 的 desc / handler / ctx / tag

这个函数的价值很高，因为它把很多本来要手动推断的偏移直接“打印证据化”了。

逆向时应该频繁回来看它，修正结构体字段名。

## 4. 建议的逆向顺序

### 第一步：看 `main`

先不要试图读懂前面的所有混淆计算。`main` 做了两件事：

1. 初始化一批状态。
2. 最终进入 `run_gateway_menu`。

所以 `main` 只需要确认：

- 最终 runtime state 指针如何构造。
- 有哪些初始化字段进入菜单前已经设好。

前面那段状态混合逻辑不是第一优先级。

### 第二步：看 `run_gateway_menu`

把菜单 case 和函数名一一对应。

完成后你要有一张这样的脑图：

- `1 -> register_model_artifact`
- `2 -> stream_artifact_chunk`
- `3 -> bootstrap_async_scheduler`
- `4 -> inspect_scheduler_queue`
- `5 -> allocate_session_tensor`
- `6 -> complete_batch_inference`
- `7 -> patch_session_metadata`
- `8 -> provision_worker_profile`
- `9 -> dispatch_async_task`
- `10 -> runtime_telemetry`
- `11 -> handbook`

### 第三步：恢复 artifact 链

先看 `register_model_artifact`：

- 输入 `manifest.items`
- 输入 `manifest.stride`
- 计算 `declared_bytes = items * stride`
- `calloc` 一块 artifact arena

再看 `stream_artifact_chunk`：

- 输入 `stream.offset`
- 输入 `stream.payload.hex`
- 解析十六进制到临时 byte buffer
- 仅允许 offset 落在很靠前的窗口内
- 最多写到 declared boundary 附近

这条链告诉你：artifact 输入面不是无限制写，它有窗口策略。

### 第四步：恢复 scheduler 链

`bootstrap_async_scheduler` 会：

- 分配 scheduler ctrl
- 构造 8 个 task descriptor
- 给每个 task 填不同 handler
- tag 形如 `sqe-%zu`

然后看：

- `inspect_scheduler_queue`
- `dispatch_async_task`

其中 `dispatch_async_task` 会检查 handler 是否在白名单中。说明 scheduler 这条线不是第一优先利用点，但它能帮助恢复 task descriptor 布局：

```c
struct task_desc {
    uint64_t task_id;      // +0
    uint64_t ???;          // +8
    uint64_t ???;          // +16
    void (*handler)(...);  // +24
    void *ctx;             // +32
    char tag[32];          // +40
};
```

### 第五步：恢复 session 链

这是最关键的一步。

先看 `allocate_session_tensor`：

- 分配 `0x50` 字节 session 对象
- 分配 payload buffer
- alias 写入 `+16`
- 默认 `postproc_fn = postproc_xor_scramble`
- 标记 slot active

再看 `complete_batch_inference`：

- 判断 slot active
- 调用 `postproc_fn`
- free payload
- delete session
- active 标记清零

做完这一步后，你应该在 IDA 里把 session 结构字段名基本恢复出来。

### 第六步：单看 `patch_session_metadata`

这一阶段不要再当普通业务逻辑看了，要当漏洞面看。

重点确认：

1. 它拿到的 session 指针来自哪个数组。
2. 为什么要求 slot inactive。
3. 改的是对象首 qword，对应哪个语义。
4. 写完后，哪个后续路径还会再次使用这块已释放对象。

如果后续某路径还会把 stale pointer 当合法对象解引用，那么这里就是题眼。

### 第七步：用 `runtime_telemetry` 做交叉验证

telemetry 不是利用点，但它是恢复布局最有效的“打印版结构图”。

你应该反复比对：

- telemetry 里打印的 handle
- 实际数组槽位保存的值
- session 的 q0、q1
- scheduler.head 的 handler / ctx / tag

用打印语义给结构体字段命名。

## 5. 在 IDA 里的具体使用过程

## 5.1 初始摸底

### A. 先看字符串窗口

打开 `Shift+F12` 看字符串，优先搜：

- `flag`
- `snapshot`
- `scheduler`
- `session`
- `diag`
- `telemetry`
- `gateway>`

目的不是直接找漏洞，而是快速找到主业务区域。

### B. 对关键字符串按 `X` 看交叉引用

例如：

- `"/flag"`
- `"[audit] snapshot: "`
- `"session.tensor_bytes> "`
- `"diagnostic offset policy allows qword_index=0 only"`

这些字符串基本可以直接把你带到核心函数。

## 5.2 从函数图切回高层逻辑

### A. 进主菜单函数后先切伪代码

快捷键：

- `F5`：Hex-Rays 伪代码
- `Tab`：汇编/伪代码切换

进入 `run_gateway_menu` 后，不要先看汇编，先在伪代码里认出 switch-case。

### B. 给 case 目标函数立即重命名

操作建议：

1. 光标放到目标函数调用处。
2. 按 `Enter` 跳进去。
3. `N` 重命名函数。

命名原则：

- 先按“行为”命名，不要过度猜语义。
- 例如先叫 `allocate_session_tensor`，而不是一开始起成 `uaf_prepare_stage2`。

## 5.3 恢复结构体的方法

### A. 不要一开始就建完整结构体

建议先做三步：

1. 在伪代码里记下固定偏移。
2. 用注释把偏移含义标上。
3. 等至少确认 4 到 6 个字段后再建结构体。

比如 session：

- `+8` 被 `malloc/free`
- `+4` 被当 size
- `+16` 被 `snprintf`
- `+56` 被当函数指针调用

这时候再建结构最稳。

### B. 在 IDA 中建结构体

常用方式：

1. 打开 `Local Types`
2. 新建结构体声明
3. 把已确认字段写进去

例如可以先写：

```c
struct session_obj {
    uint32_t slot_id;
    uint32_t payload_size;
    void *payload_ptr;
    char alias[32];
    uint64_t generation;
    void (*postproc_fn)(struct session_obj *);
};
```

然后把相应指针类型套回去。

### C. 对数组槽位也要命名

runtime state 里有明显数组：

- task descriptor 数组
- session handle 数组
- active bitmap
- autoscaler profile vector

即便暂时不知道 runtime state 全结构，也要先把这些偏移注释出来。

## 5.4 恢复函数指针语义

看到这种形式时：

```c
v17 = *(__int64 (__fastcall **)())(v11 + 56);
((void (__fastcall *)(__int64))v17)(v11);
```

就要立即认定这是对象字段里的函数指针。

接着做两件事：

1. 找所有把某个函数地址写到这个偏移的地方。
2. 找所有合法候选函数。

这里已经确认有三种 postproc：

- `postproc_xor_scramble`
- `postproc_clear_negative_bytes`
- `postproc_shift_right_bytes`

## 5.5 用 xref 和 telemetry 验证恢复结果

做法：

1. 找字符串 `diag.audit_sink=`
2. 跳到 telemetry
3. 看它打印的是哪个函数地址
4. 再回到那个函数地址确认是不是 `audit_snapshot_read_flag`

这种“打印语义 -> 地址 -> 实现”的三点校验，恢复精度最高。

## 5.6 注释策略

不要写大段泛注释，建议只写三种：

### A. 控制流注释

例如：

- `main menu dispatcher`
- `session lifecycle end`
- `recycled session only`

### B. 结构偏移注释

例如：

- `session->payload_ptr @ +8`
- `task_desc->handler @ +24`

### C. 利用相关注释

例如：

- `stale pointer remains in slot array after delete`
- `constrained qword write into recycled session`
- `direct /flag read sink`

## 6. 当前应重点盯的利用面

目前从静态逆向结果看，最值得盯的是：

### 6.1 recycled session + stale pointer

`complete_batch_inference` 删除对象后，没有把 slot 里的指针清空。

这意味着后续函数如果继续使用这个 slot 里的指针，就会变成：

- UAF
- stale object field rewrite
- 函数指针伪造

### 6.2 `patch_session_metadata` 只写首 qword

这个限制很明显，说明题目不是让你直接任意改整个对象，而是要你结合对象布局去利用首字段的语义。

接下来要重点判断：

- session 首 qword是否可能参与后续虚假对象解释
- 是否有别的路径会把 stale 指针重新当作别的类型解释

### 6.3 audit sink 地址已经明确

`audit_snapshot_read_flag` 已经是清晰目标。

如果能通过：

- 函数指针劫持
- handler 改写
- ctx 伪造

把流程导向它，就有直接出 flag 的可能。

## 7. 推荐的实际操作顺序

如果你现在继续自己在 IDA 里推进，按这个顺序最省时间：

1. 打开 `run_gateway_menu`，把 1-10 号菜单全部记清。
2. 看 `register_model_artifact` 和 `stream_artifact_chunk`，确认 artifact 写入边界。
3. 看 `allocate_session_tensor`，建 `session_obj` 结构体。
4. 看 `complete_batch_inference`，把 session 生命周期注释完整。
5. 看 `patch_session_metadata`，确认受限写对哪个字段生效。
6. 看 `runtime_telemetry`，修正 runtime state 和 task_desc 字段名。
7. 最后回到 `audit_snapshot_read_flag`，把触发链和目标地址关系闭环。

## 8. 一句话判断题眼

当前静态结果最像的题眼是：

`session` 在完成推理后被释放，但句柄数组残留 stale pointer；随后诊断 patch 功能可以在“仅允许 recycled session”的条件下改写该对象首 qword；结合后续对 session 或相关函数指针/上下文的再次使用，存在构造控制流或数据流到 `audit_snapshot_read_flag` 的可能。

---

如果后续继续做，下一步最合理的是：

1. 动态跑程序，按菜单实际走一遍 session 创建/回收/patch/telemetry。
2. 验证 stale pointer 在回收后是否仍被 telemetry、dispatch 或其他路径继续解引用。
3. 再决定是走 UAF 方向，还是走函数指针/上下文伪造方向。
